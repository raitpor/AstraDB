# AstraDB 场景文档

> 版本：v1.0（设计稿） · 语言：中文 · 状态：待评审
> 定位：**大数据量时间分片快照高压缩数据库**——描述本应用要解决的问题与适用场景。

---

## 1. 要解决的问题

### 1.1 问题陈述

存在一类数据负载：系统按周期或**非固定间隔**（被动导入）对**大量实体**（点）做一次**全量快照**，每个快照包含所有实体的当前状态（若干数值/枚举字段）。这类负载的特点是：

- **周期性全量**：每次快照是完整集合，而非单点增量；
- **时间轴非固定间隔**：快照按实际到达时刻落盘（被动导入），支持任意间隔
- **大数据量**：单快照数十万行级，长年累积后总量达百亿行级；
- **压缩敏感**：历史全量快照是海量数据，**存储成本主导**，须最大化压缩；
- **回查需求**：按时间点取历史全量快照、按点与时间点取值。

### 1.2 为什么通用数据库/时序数据库不是最优解

| 方案 | 问题 |
|---|---|
| 关系库（Oracle/PostgreSQL） | 行式存储每行固定列开销 + 双索引冗余，同数据量为自研的 **~12 倍**；索引随数据线性膨胀 |
| 通用时序数据库（InfluxDB/Prometheus/VictoriaMetrics） | 面向**动态序列流**：每点携带标签/独立时间戳/序列注册，需倒排索引；对"固定点集 + 周期性全量快照"负载，空间为自研的 **10 倍以上**，且"按时间点取全量快照"是低效操作 |
| 通用列式库（ClickHouse/Parquet） | 压缩率依赖通用编码（无 Gorilla 类时序编码），高基数浮点/小整数场景不如自研；且无内建的快照窗口与时间分片语义 |

## 2. 数据特征与规模参数

| 参数 | 取值 | 说明 |
|---|---|---|
| 行数 N | 十万级 | 大数据量级，可扩展至 50 万+/百万行 |
| 快照频率 | **非固定间隔**（被动导入；） | 任意间隔均支持，等间隔为特例 |
| 字段 | 多列，按表注册信息（可变：数值/字符串） | 主键列 + 若干值列 |
| 点增长 | 缓慢增长 | 数月一批 / 随机日期少量、一天内随机时刻加入 |
| 主键 | 唯一（写入前校验）；每表记录主键列 | 快照写入后**不可增点**（不可变） |
| 保留期 | **5 年**（默认，可配置） | 超期段文件滚动清理 |
| 表 | 多表（`data/<表>/{manifest,schema-registry,segments}`） | 表名必填，互不干扰 |
| 表结构| schema冻结，不允许修改列数和列类型 | 标注表包含字段以及主键列 |

## 3. 适用场景

- **设备/资产周期状态快照**：按周期（间隔可非固定）采集全量设备状态（点位、参数、类型），需要回查任意时刻的全量状态与单设备历史曲线；
- **台账/库存周期盘点**：周期性全量盘点（每轮全量快照一次），保留多年用于追溯与对比；
- **合规追溯**：全量历史快照长期保留，支撑审计与问题定位（"某时刻某点是什么状态"）；
- **数据特征匹配**：点集基本稳定 + 缓慢增长、快照全量（间隔非固定，等间隔为特例）、读多写少（周期写 + 回溯查）、压缩率优先。

## 4. 不适用场景

- **实时监控/告警**：毫秒~秒级流式写入、持续滚动查询（AstraDB 写入为分钟级快照批量）；
- **标签动态检索**：需要 `WHERE region="华东" AND type=2` 类跨维度过滤（无标签索引）；
- **点集高频变动**：点增删频繁、无固定点集（窗口聚合依赖行数一致性，高频变动会导致窗口碎片化）；
- **稀疏/偶发单点写入**：不是"周期性全量快照"而是任意时间戳的偶发单点写入（无全量快照形态）——此类负载压缩收益下降，且与快照模型不匹配。
- **需频繁更新已写数据**：快照不可变，不支持改历史。

## 5. 与通用方案量化对比

| 指标 | AstraDB（自研） | 通用 TSDB | Oracle（行式+索引） |
|---|---|---|---|
| 存储（假设N=20 万，年化） | **~175 GB/年** | ~1.7 TB+/年（10 倍） | ~2.0 TB/年（11~12 倍） |
| 快照全量读取 | O(1) 定位 + 分页 | 全序列扫描 | 全表扫 + 索引 |
| 单点序列查询 | 主键列匹配（按 N 优化） | 标签索引 | 二级索引 |
| 标签/维度过滤 | 不支持 | 支持 | 支持 |
| 动态点集 | 缓慢增长（年增 ≤1 万） | 任意 | 任意 |
| 写入语义 | 分钟级全量快照 | 流式单点 | 事务 |

> 结论：本应用**牺牲通用检索能力，换取快照场景下极致的压缩率与全量快照读取效率**——适用于"周期性全量快照 + 长期保留 + 回溯查询"的数据负载。

## 6. 非功能约束

| 维度 | 约束 |
|---|---|
| 压缩率 | 优先（CPU 换空间），压缩等级可配置 |
| 保留期 | 根据配置每个表保留指定数据文件数（保留天数）；Segment 文件不可变，便于归档迁移 |
| 单快照写入时延 | 20 万行编码 + 压缩 ≤ 5s |
| 查询时延 | 单快照全量读取 ≤ 2s； |
| 内存 | 缓冲 2~4 个快照 ≤ 100MB，禁止装箱对象驻留 |
| 崩溃恢复 | 进程崩溃不产生半写可见数据，未完成快照可安全丢弃/重导 |

### 7 文件组织

```
data/
├── tables.json                  # 表元数据，记录本数据库存在的表
└── tableName1                   # 表名，支持多表
  ├── manifest.json              # 分片清单（可重建）
  ├── schema-registry.json       # schema 版本历史
  └── segments/
      └── 2026/
          ├── 2026-01-01.seg     # 当天全部快照
          ├── 2026-01-02.seg
          └── ...
└── tableName2
```

**Segment 文件布局（.seg，按天分片、追加写）**：

```
┌────────────────────────────────────────────────┐
│ FileHeader: magic(4B) 格式版本(2B) 布局(1B)     │
│             段起始时间(8B) schemaVersion(2B)    │
│             列数(2B)                            │
├────────────────────────────────────────────────┤
│ Chunk 0   (快照0)                           │
│ Chunk 1   (快照1)                           │
│ ...                                             │
│ Chunk n (快照n)                           │
├────────────────────────────────────────────────┤
│ ChunkIndex: 每 chunk 一条                        │
│   offset(8B) length(4B) 时间戳(8B) 行数(4B)      │
│   schemaVersion(2B) CRC32C(4B)                  │
├────────────────────────────────────────────────┤
│ Footer: magic(4B) 索引偏移(8B) 索引条目数(4B)     │
│         文件校验和(8B) 结束magic(4B)             │
└────────────────────────────────────────────────┘
```

## 8. 一句话定位

**AstraDB 是专为"大数据量、周期性全量快照、长期高压缩保留"设计的时序化列式存储**：以时间分片组织快照、以时间序列编码压缩值列、以主键列匹配检索点，用最小的空间保存任意历史时刻的全量状态。
